# 设计稿审核 Skill

审核 Figma 设计稿是否符合品牌设计规范和合规要求，输出结构化评分报告。

---

## 触发条件

以下任一情况激活此 Skill：
- 用户提供 Figma 链接并要求审核/检查/review
- 用户说"审核这个设计"、"检查规范"、"合规检查"
- 用户使用 `/audit-design-system <Figma URL>`

---

## Figma 组件库（优先审核来源）

审核时优先引用以下两个 Figma Library，检查设计稿是否正确使用了库中的组件实例和 Token 变量：

| 库名称 | 用途 | 审核重点 |
|--------|------|---------|
| **设计组件库2026** | 组件规范 | 检查是否使用组件实例（vs 自绘 frame） |
| **🎨2026_token** | Token 规范 | 检查颜色/间距/圆角是否绑定 Token 变量 |

**优先级规则**：
1. 先通过 `search_design_system` 在上述库中查找对应组件/Token，判断设计稿是否正确引用
2. 库无法覆盖的逻辑规则（合规、状态覆盖、交互规范）再对照 specs/ 规范文件检查

---

## 审核流程

### Step 1：解析输入

接受完整 Figma URL 或 `fileKey` + `nodeId`。
将 node ID 中的 `72-293` 格式标准化为 `72:293`。

如果用户未指定市场，默认按 EU 通用市场处理。
如果用户指定法国站或 URL 含 FR 相关信息，追加 FR 规则。

### Step 2：拉取设计数据

使用 Figma MCP 工具获取最小必要数据：
- `get_figma_data`：获取节点结构、属性、样式绑定
- 截图：视觉确认

对于大型画板，先用 `get_figma_data` 的顶层结构识别关键模块，再逐一深入。

### Step 3：库级检查（优先）

调用 `search_design_system` 检查：

**Token 绑定检查（🎨2026_token）**：
- 所有颜色填充/描边是否绑定了 Token 变量（而非硬编码 hex）
- 间距值是否使用 Token（允许值：2/4/6/8/10/12/16px）
- 圆角是否引用 Token
- 字号/字重是否引用 Token

**组件实例检查（设计组件库2026）**：
- 识别设计中的 UI 元素（按钮、卡片、输入框、导航等）
- 检查它们是否为库中组件的实例
- 如果是自绘 frame 但库中有对应组件 → 标记为问题

### Step 4：规范规则检查

按需加载 `~/tasks/ai-workflow/specs/` 中的规范文件，按以下顺序检查：

#### 4.1 合规检查（默认 EU，法国追加 FR）

加载文件：
- 始终：`regulations/合规知识库-欧盟通用EU.md`
- 法国站：追加 `regulations/合规知识库-法国站FR.md`

检查项：
- [ ] 是否展示了销量信息（无口径）
- [ ] 是否有库存紧张文案（"Only X Left"等）
- [ ] 是否有虚假/夸大限时活动
- [ ] 是否有催促性文案（"Hurry up"等）
- [ ] 弹窗确认/取消按钮是否视觉权重相同
- [ ] 关闭按钮触控区是否 ≥ 44px
- [ ] 每个违规项标注规则编号（如 EU-D-001）

#### 4.2 Token 规则检查

加载文件：`tokens/colors.md`、`tokens/spacing.md`（始终），其余按需

检查项：
- [ ] 所有颜色值是否在 Token 范围内
- [ ] 间距是否在梯度内（2/4/6/8/10/12/16px）
- [ ] 圆角值是否使用 Token
- [ ] 字号/字重是否使用 Token
- [ ] 同页字号层级是否超过 4 层
- [ ] 正文字号是否 ≥ 12px

#### 4.3 组件规则检查

加载文件：仅加载设计中涉及的组件规范（`components/*.md`）

检查项：
- [ ] Primary 按钮每屏是否唯一
- [ ] 弹窗/浮层是否由用户操作触发（非自动弹出）
- [ ] 是否存在弹窗嵌套弹窗
- [ ] 列表页是否包含骨架屏/空态/错误态
- [ ] 表单提交按钮未满足必填时是否为 Disabled 态
- [ ] 破坏性操作是否有二次确认
- [ ] 是否有自绘元素可替换为组件库组件

#### 4.4 布局检查

加载文件：根据平台加载 `layout/mobile.md` 或 `layout/pc.md`

检查项：
- [ ] 页面左右边距是否为 16px
- [ ] 可点击元素触控区是否 ≥ 44×44px
- [ ] 移动端是否有底部安全区处理
- [ ] 是否在移动端使用了 PC 端专属组件

### Step 5：评分与输出

始终加载 `audit-scoring.md` 作为评分规则参考。

## 评分规则

### 分数计算

| 维度 | 权重 | 满分 |
|------|------|------|
| 合规得分 | 50% | 100 |
| 规范得分 | 50% | 100 |

**综合得分 = 合规得分 × 0.5 + 规范得分 × 0.5**

### 问题扣分

| 等级 | 扣分 | 定义 |
|------|------|------|
| 🔴 Critical | -25 | 合规红线，必须修改才能上线 |
| 🟠 High | -15 | 严重规范违反，影响体验或一致性 |
| 🟡 Medium | -8 | 规范偏差，视觉或交互不一致 |
| ⚪ Low | -3 | 轻微偏差，建议修改 |

### 综合评级

| 评级 | 分数 | 含义 |
|------|------|------|
| ✅ Pass | 90–100 | 可直接上线 |
| ⚠️ Review | 70–89 | 修改后复审 |
| ❌ Fail | 0–69 | 必须返工 |

## 规范文件位置

所有规范文件位于 `~/tasks/ai-workflow/specs/`：

```
specs/
├── index.md              ← 模块索引
├── constraints.md        ← 全局禁止事项（每次必加载）
├── audit-scoring.md      ← 评分规则
├── tokens/               ← Token 规范
├── components/           ← 组件规范
├── layout/               ← 布局规范
└── regulations/          ← 合规知识库
```

---

## 注意事项

- 每个问题必须定位到具体 Figma 节点（提供 node ID）
- 合规问题必须标注规则编号（如 EU-D-001、FR-P-002）
- 不要标记纯审美偏好问题，只标记客观规范违反
- 如果设计中某个元素在组件库中找不到对应组件，说明"库中暂无此组件"而非强行匹配
- 对于库和 specs 描述冲突的情况，以 Figma 组件库为准（库是最新的 source of truth）
- 规范文件中仍有 `【填入 xxx】` 占位符的字段跳过不检查，不影响评分
